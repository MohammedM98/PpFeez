# PpFeez — المواصفات التفصيلية الكاملة

تطبيق سطح مكتب (ويندوز) لإدارة معاملات PayPal وتوزيعها على العملاء.

---

## 1. السياق والقرارات

صاحب المشروع يستقبل على حساباته **الشخصية** في PayPal تحويلات تخصّ عملاء مختلفين (أحمد، علي...). يريد برنامجاً يستخدمه وحده:

1. يتصل ببريد Gmail، وعند الضغط على "سحب" يقرأ رسائل PayPal ويجمع المعاملات في جدول واحد.
2. يخصّص كل معاملة يدوياً لعميل، ثم يسجّل موافقة العميل (الموافقة تتم خارج البرنامج).
3. يحفظ لكل معاملة: الأصلي، رسوم PayPal، الصافي.
4. يطبّق عمولة لكل عميل (افتراضي 25%، قابلة للتعديل لكل معاملة) **على الصافي بعد رسوم PayPal**.
5. دفتر حساب لكل عميل **برصيد منفصل لكل عملة**.

| القرار | الاختيار | السبب |
|---|---|---|
| الشكل | تطبيق سطح مكتب، ويندوز | مستخدم واحد، البيانات على الجهاز، بلا استضافة |
| التقنية | Tauri 2 + React | قلب Rust خفيف، واجهة React جميلة تدعم RTL |
| مصدر المعاملات | Gmail عبر IMAP + كلمة مرور تطبيق | Google OAuth طلب فوترة؛ PayPal API غير متاح للحساب الشخصي |
| السحب | يدوي بزر | طلب صاحب المشروع |
| الموافقة | المدير يسجّلها | لا بوابة للعملاء |
| العملات | رصيد منفصل لكل عملة | بلا تحويل |
| المستودع | `MohammedM98/PpFeez` (فارغ)، الجذر، فرع `main` | |

## 2. التقنيات

- **الواجهة**: React + TypeScript + Vite + Tailwind + shadcn/ui، React Router، TanStack Query، TanStack Table، react-hook-form + zod.
- **القلب**: Rust. crate مستقل `ppfeez-core` بلا اعتماد على Tauri (كل المنطق والاختبارات فيه)، و`src-tauri` طبقة أوامر رقيقة فوقه.
- **القاعدة**: SQLite عبر `rusqlite` (bundled)، وضع WAL، `foreign_keys=ON`، migrations مرقّمة تُطبَّق عند التشغيل.
- **البريد**: IMAP على `imap.gmail.com:993` (TLS)، تحليل MIME بـ `mail-parser`، استخراج من HTML بـ `scraper`.
- **الأسرار**: كلمة مرور تطبيق Gmail في Windows Credential Manager عبر `keyring`. كلمة قفل البرنامج hash بـ `argon2`.
- **البناء**: GitHub Actions (`tauri-apps/tauri-action`، `windows-latest`) يُخرج مثبّت NSIS `.exe`.

> على جلسة التنفيذ التحقق من الإصدارات الحالية لـ Tauri 2 ومكتبات Rust من وثائقها قبل الاعتماد عليها.

### اصطلاحات عامة
- **المبالغ**: `INTEGER` بأصغر وحدة للعملة (سنت). لا float في أي مكان، لا في Rust ولا في TypeScript (الواجهة تستقبل الأعداد الصحيحة وتنسّقها فقط).
- **خانات العملة**: 2 افتراضياً؛ 0 لـ `JPY, HUF, TWD`. دالتان فقط للتحويل: `parse_amount(text, currency)` و`format_amount(minor, currency)`.
- **التواريخ**: تُخزَّن UTC بصيغة ISO-8601 نصاً، وتُعرض بتوقيت الجهاز بصيغة `YYYY-MM-DD HH:mm`، تقويم ميلادي.
- **الأرقام**: لاتينية (0-9) دائماً، والمبالغ تُعرض LTR داخل الواجهة RTL مثل `1,250.00 USD`.
- **النسب**: basis points (`2500` = 25.00%)، تُعرض بخانتين عشريتين.
- **اللغة**: عربية فقط، نصوص الواجهة في ملف واحد `src/lib/strings.ts`.

## 4. القواعد المحاسبية

### 4.1 الحساب
```
net        = gross − fee
commission = percent: round_half_up(net × bps / 10000)
             fixed:   المبلغ المدخل (0 ≤ commission ≤ net)
للعميل      = net − commission
```
مثال: 100.00 أصلي، رسوم 5.00، صافي 95.00، عمولة 25% = 23.75، للعميل 71.25.
التقريب half-up بأعداد صحيحة: `(net × bps + 5000) / 10000`.

### 4.2 دورة حياة المعاملة

```
                 تخصيص                اعتماد
 unassigned ───────────► pending_approval ───────────► approved
     ▲  ▲                     │                           │
     │  └──── إلغاء التخصيص ───┘                           │
     │                                                    │
     └─────────── إلغاء الاعتماد (قيد عكسي) ◄───────────────┘
     │
     └──► excluded (ليست لأي عميل: مدفوعات تخصّني)  ◄──► unassigned
```

| الانتقال | الشرط | الأثر |
|---|---|---|
| تخصيص | الحالة `unassigned`، العميل نشط | ينسخ `default_commission_bps` من العميل، `commission_mode=percent`، يحسب المبالغ إن وُجدت الرسوم |
| تعديل العمولة | الحالة `pending_approval` | يعيد الحساب |
| تعديل الرسوم/الصافي | الحالة ≠ `approved` | يُدخل أحدهما ويُحسب الآخر؛ `fee_is_estimated=0`؛ يعيد حساب العمولة |
| اعتماد | `pending_approval` **و** `fee_minor` غير فارغة **و** `customer_amount_minor > 0` | في transaction واحدة: الحالة `approved` + قيد `credit` واحد بتاريخ اليوم |
| إلغاء التخصيص | `pending_approval` | يمسح العميل والعمولة |
| إلغاء الاعتماد | `approved`، مع تأكيد وسبب إلزامي | قيد `reversal` بسالب مبلغ القيد الأصلي (`reverses_entry_id`)، الحالة ترجع `unassigned` |
| استبعاد/إرجاع | `unassigned` ⇄ `excluded` | لا أثر مالي |

- المعاملة المعتمدة **مقفلة**: لا تعديل للرسوم أو العمولة أو العميل إلا بإلغاء الاعتماد ثم إعادة الاعتماد.
- كل انتقال يُكتب في `audit_log`.
- التخصيص والاعتماد الجماعي: كل معاملة في transaction خاصة، والنتيجة تعرض "نجح N، فشل M" مع سبب كل فشل.

### 4.3 الرسوم المفقودة
- رسائل الحساب الشخصي غالباً لا تذكر الرسوم ⇒ `fee_minor = NULL` وشارة **"تحتاج رسوم"**.
- المدير يُدخل الرسوم **أو** الصافي (كما في رصيد PayPal)، أو يضغط **"بلا رسوم"** (= 0).
- **تقدير اختياري** (من الإعدادات، معطّل افتراضياً): نسبة + مبلغ ثابت (مثل 4.4% + 0.30). عند تفعيله يُقترح في حقل الرسوم بلون مختلف مع نص "تقديري"، ولا يُحفظ إلا بضغط المدير على "تأكيد".

### 4.4 الاسترداد والعكس
- رسالة استرداد/عكس تُنشئ صفاً `type = refund|reversal` بـ `related_txn_id` = رقم المعاملة الأصلية.
- إن كانت الأصلية **غير معتمدة**: تنبيه على الأصلية "تم استردادها"؛ المدير يستبعدها أو يعدّل.
- إن كانت الأصلية **معتمدة**: تظهر في "تنبيهات تحتاج إجراء" مع قيد `reversal` مقترح:
  - استرداد كامل: سالب كامل حصة العميل.
  - استرداد جزئي: `−(refund × customer_amount / gross)` مقرّباً، قابل للتعديل قبل التأكيد.
  - لا يُنشأ القيد إلا بتأكيد المدير.
- صفوف الاسترداد نفسها لا تُخصَّص لعميل مباشرة؛ حالتها `excluded` بعد المعالجة.

### 4.5 الدفعات والتسويات
- **دفعة (payout)**: مبلغ موجب يُدخله المدير ويُخزَّن سالباً، مع العملة، التاريخ، الطريقة (نقداً/تحويل بنكي/USDT/PayPal/أخرى)، مرجع، ملاحظة. إن تجاوزت الرصيد: تحذير وتأكيد صريح (يُسمح بالرصيد السالب ويظهر بالأحمر "عليه").
- **تسوية (adjustment)**: موجبة أو سالبة مع وصف إلزامي (رصيد افتتاحي، خصم، تصحيح).
- **عكس قيد**: لأي قيد غير معكوس؛ ينشئ قيداً معاكساً بوصف "عكس: {الوصف الأصلي}" وسبب إلزامي.

### 4.6 العملاء
- التعطيل (`is_active=0`) يخفي العميل من قوائم التخصيص ويبقي دفتره. الحذف النهائي في 4.7.
- تغيير العمولة الافتراضية لا يؤثر على معاملات مخصّصة سابقاً.

### 4.7 الحذف (طلب صاحب المشروع)

الحذف **نهائي** ويغيّر الأرصدة، لذلك له قواعد ثابتة:
- **تأكيد يعرض الأثر قبل التنفيذ**: كل حذف يمرّ بـ "معاينة" من القلب تعرض ما سيُحذف وتغيّر الأرصدة لكل عميل وعملة، ثم تأكيد صريح.
- **لقطة في `audit_log`**: كل صف محذوف يُحفظ كاملاً (JSON) في `audit_log` بفعل `*.delete`، مع السبب إن أُدخل.
- **نسخة احتياطية تلقائية** قبل: حذف أكثر من معاملة، حذف عميل، حذف قيد، وكل "بدء من جديد". إن لم يُحدَّد مجلد نسخ: يُطلب تحديده أو متابعة صريحة.
- كل حذف داخل transaction واحدة: ينجح كله أو لا شيء.
- بعد الحذف: ملف Excel الرئيسي يعكس الحذف عند تحديثه التالي.

**1. حذف معاملة** (مفرد أو جماعي، من قائمة ⋯ وشريط التحديد):
- غير معتمدة (غير مخصّصة / بانتظار الموافقة / مستبعدة): تُحذف مباشرة بعد التأكيد.
- **معتمدة**: التأكيد يوضح "سيُحذف قيد الدفتر المرتبط ويتغيّر رصيد {العميل} بمقدار −X {عملة}". تُحذف المعاملة **وكل قيود الدفتر المرتبطة بها** (قيد الاعتماد وأي قيد عكسي لإلغاء اعتماد سابق) فيعود الرصيد كأنها لم تكن.
- صفوف الاسترداد/العكس المرتبطة بها (`related_txn_id`) تبقى، وتظهر بلا أصل.
- **لا تعود عند السحب التالي**: الرسالة الأصلية تبقى في `raw_emails` بحالة `ignored` وسبب `deleted_by_user`. يمكن استرجاعها من الرسائل ← متجاهلة ← "إعادة تحليل" (تُنشأ المعاملة من جديد غير مخصّصة).

**2. حذف عميل** (من قائمة العملاء، وزر في دفتره):
- المعاينة تعرض: عدد معاملاته (مخصّصة/معتمدة)، عدد قيوده، وأرصدته الحالية.
- التنفيذ: **كل قيود دفتره تُحذف**، ومعاملاته (معتمدة أو بانتظار الموافقة) **ترجع غير مخصّصة** (لا تُحذف؛ يمكن تخصيصها لعميل آخر).
- التأكيد بكتابة **اسم العميل** حرفياً (`confirm_mismatch` إن لم يطابق).
- البديل الأخف "تعطيل" يبقى متاحاً ويُقترح في نفس النافذة.

**3. حذف قيد من الدفتر** (قائمة ⋯ على القيد):
- **مسموح**: الدفعات، التسويات، وقيود العكس اليدوية لها. حذف قيد معكوس يحذف معه قيد عكسه (زوج). حذف قيد عكسي وحده يعيد القيد الأصلي فعّالاً.
- **غير مسموح مباشرة**: قيود الاعتماد (`credit`) وقيود إلغاء الاعتماد المرتبطة بمعاملة (`not_deletable`)؛ تُدار من المعاملة (إلغاء الاعتماد أو حذف المعاملة). القائمة تعرض السبب بدل الزر.
- التأكيد يعرض المبلغ والرصيد قبل/بعد.

**4. بدء من جديد** (الإعدادات ← البيانات ← "حذف البيانات"):
- خيارات (مربعات): **المعاملات والرسائل وسجل السحب** · **العملاء والدفاتر** · **حسابات البريد وكلمات مرورها** · **الإعدادات** (تعود للافتراضي؛ القفل يبقى ما لم يُختر).
- حذف المعاملات يصفّر `last_uid`/`uid_validity` لكل بريد فيُعاد السحب من البداية.
- حذف العملاء والدفاتر يتطلب حذف المعاملات أيضاً أو يعيدها كلها غير مخصّصة (يُذكر في المعاينة).
- المعاينة تعرض الأعداد لكل خيار. التأكيد بكتابة كلمة **"حذف"**. نسخة احتياطية **إلزامية** قبل التنفيذ ويُعرض مسارها بعده (للتراجع: الإعدادات ← النسخ الاحتياطي ← استعادة).
- حذف حسابات البريد يحذف كلمات مرورها من Windows Credential Manager.

## 5. السحب من Gmail

### 5.1 الخطوات
1. قفل: لا سحب ثانٍ لنفس البريد وهو `running`. عند تشغيل البرنامج، أي `running` قديم يُعلَّم `failed` ("انقطع").
2. اتصال IMAP، `SELECT` للمجلد، قراءة `UIDVALIDITY`.
3. تحديد المدى حسب **نطاق السحب** الذي يختاره المدير (5.5):
   - `new` (الجديد منذ آخر سحب): `UID SEARCH {PAYPAL_FROM} UID {last_uid+1}:*`. إن لم يُسحب البريد من قبل أو تغيّر `UIDVALIDITY` ⇒ كل التاريخ.
   - `last_days` و `between`: البحث بالتاريخ (5.5).
   - `all`: `UID SEARCH {PAYPAL_FROM}` (كل التاريخ).
4. الجلب على دفعات من 50 رسالة (`BODY.PEEK[]` — لا يغيّر حالة "مقروءة").
5. لكل رسالة، في transaction: تخطّي إن وُجد `message_id` ← التحقق من المصدر ← الحفظ في `raw_emails` ← التحليل ← إدراج المعاملة (تخطّي إن وُجد `paypal_txn_id` ⇒ `duplicate_count`).
6. بعد كل دفعة: تحديث `last_uid` والعدّادات، وإرسال حدث `pull://progress` للواجهة. يمكن الإلغاء بين الدفعات.
7. النهاية: `done` + `last_pulled_at`. عند خطأ: `failed` مع الرسالة، وما حُفظ يبقى (السحب التالي يكمل من `last_uid`).

### 5.6 نطاقات PayPal حسب الدولة (كل الاحتمالات)

PayPal يرسل من نطاق الدولة: صاحب المشروع يستقبل من **`service@paypal.co.il`**. البحث على `paypal.com` وحده لا يجد هذه الرسائل (سبب خلل 0.2.0: سحب ناجح بصفر رسائل). الهدف: إيجاد **أي** رسالة PayPal حقيقية من أي دولة، دون فتح الباب لرسائل مزوّرة.

**ثلاث طبقات للنطاقات**
1. **القائمة المدمجة الموثوقة**: كل نطاقات PayPal الدولية الرسمية ونطاقاتها الفرعية. على جلسة القلب جمعها والتحقق منها من مصادر PayPal الرسمية (صفحات PayPal الدولية وروابطها) وليس من الذاكرة؛ تشمل على الأقل: `paypal.com`, `paypal.co.il`, `paypal.com.tr`, `paypal.co.uk`, `paypal.de`, `paypal.fr`, `paypal.it`, `paypal.es`, `paypal.nl`, `paypal.be`, `paypal.at`, `paypal.ch`, `paypal.pl`, `paypal.se`, `paypal.dk`, `paypal.no`, `paypal.fi`, `paypal.ie`, `paypal.pt`, `paypal.ca`, `paypal.com.au`, `paypal.com.br`, `paypal.com.mx`, `paypal.jp`, `paypal.cn`, `paypal.com.sg`, `paypal.com.hk`, `paypal.ae`, `paypal.in` — أي نطاق في هذه القائمة لم يثبت أنه لـ PayPal يُحذف منها (يبقى متاحاً بالطبقة 3).
2. **نطاقات يضيفها المدير**: الإعدادات ← البريد ← "نطاقات PayPal الإضافية".
3. **نطاق PayPal غير معروف**: أي مرسل نطاقه المسجَّل (eTLD+1 حسب Public Suffix List) هو `paypal.<لاحقة عامة>` ولم يكن في الطبقتين 1-2، مع `dkim=pass` لنفس النطاق ⇒ لا يُرفض نهائياً ولا يُقبل تلقائياً: يُحفظ `ignored` بسبب `unknown_paypal_domain`، ويظهر في "الرسائل ← متجاهلة" مع زر **"الوثوق بهذا النطاق"** (يضيفه للطبقة 2 بعد تأكيد يعرض النطاق، ثم يعيد تحليل كل رسائله المتجاهلة لهذا السبب). وتنبيه في لوحة التحكم: "رسائل من نطاق PayPal غير معروف: {domain} (N)".

**البحث**: `{PAYPAL_FROM}` = `FROM "paypal"` (مطابقة جزئية واسعة، تشمل كل الدول والنطاقات الفرعية). البحث يجمع المرشحين فقط؛ القبول الفعلي في التحقق 5.2. الرسائل التي فيها "paypal" لكنها ليست من PayPal (مثل رسالة من متجر يذكر PayPal في اسم المرسل) تُحفظ `ignored: not_paypal_sender` كما هي اليوم.

**الحماية** (تبقى كما هي، على كل الطبقات): نطاق `From` الفعلي = نطاق معتمد أو فرعي منه؛ `dkim=pass` من ترويسة Google لنطاق معتمد متوافق مع `From`. تُرفض: `paypal.co.il.evil.com`، `paypal-co-il.com`، `paypa1.com`، `paypal.com@evil.com` في الاسم الظاهر، و`From` معتمد مع DKIM لنطاق آخر.

**بعد التحديث**: سحب "كل الرسائل" يجد الرسائل التي فاتت؛ لا شيء يُكرَّر.

### 5.5 نطاق السحب (الجديد / آخر N يوم / من تاريخ إلى تاريخ / الكل)

زر "سحب المعاملات" يفتح نافذة صغيرة يختار فيها المدير:

| الخيار | المعنى |
|---|---|
| الجديد منذ آخر سحب | الافتراضي. غير متاح إن لم يُسحب البريد من قبل (يظهر بجانبه "لم يُسحب بعد") |
| آخر 7 أيام · آخر 30 يوماً · آخر 90 يوماً | من (اليوم − N + 1) إلى اليوم |
| من تاريخ إلى تاريخ | تاريخان شاملان بتوقيت الجهاز؛ لا مستقبل؛ `from ≤ to` |
| كل الرسائل | كل التاريخ، مع تنبيه "قد يستغرق وقتاً طويلاً" |

- الاختيار الافتراضي عند أول سحب لبريد جديد: **آخر 30 يوماً**.
- إن كان للمدير أكثر من بريد: قائمة لاختيار البريد في نفس النافذة.
- **التنفيذ بالتاريخ**: تواريخ IMAP (`SINCE`/`BEFORE`) أيام بلا توقيت وبتوقيت الخادم، لذلك يُوسَّع البحث يوماً من كل طرف: `UID SEARCH {PAYPAL_FROM} SINCE {from−1} BEFORE {to+2}`، ثم تُفلتر كل رسالة بتاريخ ترويسة `Date` محوّلاً لتوقيت الجهاز ضمن `[from, to]`. الرسائل خارج النطاق تُتخطى ولا تُحسب ولا تُحفظ.
- **التكرار آمن**: سحب نفس الفترة مرتين لا يضيف شيئاً (الرسائل المحفوظة تُعدّ `duplicate`).
- **`last_uid`** بعد أي نطاق = `max(last_uid, أكبر UID جُلب)` (الـ UIDs تتزايد مع الزمن، فـ "الجديد منذ آخر سحب" يبقى صحيحاً)، ويُحدَّث `uid_validity` إن تغيّر.
- `pull_runs` يحفظ النطاق (`range_kind`, `range_from`, `range_to`)، ويظهر في شريط التقدّم وسجل السحب، مثل "آخر 30 يوماً" أو "2026-01-01 ← 2026-03-31".
- نطاق غير صالح ⇒ `invalid_range`.

### 5.2 التحقق من المصدر (قبل أي تحليل)
تُقبل الرسالة فقط إذا تحقق **الاثنان**:
- نطاق عنوان `From` الفعلي (لا الاسم الظاهر) هو **نطاق PayPal معتمد** أو نطاق فرعي منه (مثل `intl.paypal.com`, `mail.paypal.co.il`).
- ترويسة `Authentication-Results` التي أضافها `mx.google.com` (أول ترويسة من الأعلى باسم `Authentication-Results` بالضبط، لا `ARC-Authentication-Results`) تحتوي `dkim=pass` مع `header.d` (أو `header.i`) **نطاق PayPal معتمد**، ويطابق نطاق `From` أو يكون نطاقاً أباً له (alignment).

**نطاقات PayPal المعتمدة** (5.6): القائمة المدمجة + ما يضيفه المدير في الإعدادات.

غير ذلك: `parse_status = ignored` مع السبب. هذا يمنع رسالة مزوّرة من إنشاء معاملة وهمية.

### 5.3 المحلّلات
```rust
trait PaypalParser {
    fn name(&self) -> &'static str;
    fn matches(&self, email: &ParsedEmail) -> bool;
    fn parse(&self, email: &ParsedEmail) -> Result<ParsedTransaction, ParseError>;
}
```
**أنواع الرسائل المالية المغطّاة** (كلها واردة إلى صاحب الحساب):

| النوع | أمثلة الموضوع (EN) | النتيجة |
|---|---|---|
| استلام مبلغ (أصدقاء وعائلة) | "You've got money", "You received money" | `payment` |
| استلام دفعة بضائع/خدمات | "You received a payment", "Payment received from …", "Notification of payment received" | `payment` |
| دفع طلب أموال/فاتورة | "… paid your request", "Invoice … paid" | `payment` |
| دفعة اشتراك/دفعة جماعية | "You received a subscription payment", "You've received a mass payment" | `payment` |
| eCheck معلّق ثم مكتمل | "eCheck pending", "eCheck cleared" | `payment`؛ المعلّق يُعلَّم "معلّق" ولا يُعتمد حتى تصل رسالة الاكتمال لنفس الرقم (تُحدَّث نفس المعاملة) |
| مبلغ محجوز (on hold) | "Your payment is on hold" | ملاحظة "محجوز" على المعاملة لنفس الرقم (لا معاملة جديدة) |
| استرداد أرسلته | "You sent a refund", "Refund to …" | `refund` |
| عكس/نزاع/استرجاع بنكي | "Payment reversed", "Dispute", "Chargeback", "Case …" | `reversal` |

- **اللغات**: الإنجليزية، العبرية (PayPal إسرائيل)، العربية، التركية. لكل نوع × لغة: كلمات الموضوع والعناوين (Transaction ID / מספר עסקה / رقم المعاملة / İşlem numarası، Amount / סכום / المبلغ / Tutar، Fee / עמלה / رسوم / Ücret، Net / נטו / الصافي / Net …) في جداول بيانات منفصلة عن المنطق (`paypal/lang/{en,he,ar,tr}.rs`) لتسهل إضافة لغة. أرقام الاتجاهين وعلامات التحكم في الاتجاه (LRM/RLM/isolates) تُزال قبل التحليل.
- **المحلّل العام (احتياطي)** `GenericParser`، آخر من يُجرَّب: إن لم يطابق محلّل متخصص لكن الرسالة من PayPal موثّقة وفيها **رقم معاملة PayPal** (17 حرفاً/رقماً كبيرة) **ومبلغ بعملة** ⇒ تُنشأ المعاملة مع `needs_review = 1` وسبب "صيغة غير معروفة — راجع البيانات". النوع يُستنتج إن أمكن وإلا `payment`.
- **مراجعة**: معاملة `needs_review` تظهر بشارة "تحتاج مراجعة" ولا تُعتمد حتى يضغط المدير **"تأكيد البيانات"** (يمكنه تعديل المبلغ/العملة/المرسل قبلها عبر نافذة تعديل). يُسجَّل في `audit_log`.
- رسائل PayPal غير المالية (تسجيل دخول، عروض، كشوف، "You sent a payment"، إيصالات مشترياتك) ⇒ `ignored: not_transactional`.
- رسالة مالية بلا رقم معاملة أو بلا مبلغ يمكن استخراجه ⇒ `failed` مع اسم الحقل الناقص.

الحقول: `paypal_txn_id` (إلزامي)، `gross` + `currency` (إلزامي)، `occurred_at` (من الرسالة، وإلا تاريخ الاستلام)، `payer_name`, `payer_email`, `payer_note`, `fee`, `related_txn_id` (اختيارية).
تحليل المبالغ يدعم: `$1,234.56 USD`، `1.234,56 EUR`، `€50,00`، `100.00 USD`، `₪1,234.56 ILS`.

تحليل المبالغ أيضاً: الرمز قبل الرقم أو بعده، المسافة الضيقة كفاصل آلاف، `ILS`/`₪`، `TRY`/`₺`، `USD`/`$`/`US$`، `EUR`/`€`، `GBP`/`£`، والرقم داخل نص RTL.

**العينات الحقيقية لها الأولوية**: محلّلات العبرية/العربية/التركية مبنية على أفضل معرفة متاحة وقد تخطئ؛ المحلّل العام يلتقط ما تفوته (مع مراجعة). حين يرفق صاحب المشروع رسائل `.eml` حقيقية (خصوصاً من `paypal.co.il`) تُضاف للاختبارات وتُضبط المحلّلات عليها.

> لا توجد رسائل حقيقية بعد. تُبنى المحلّلات على الشكل الإنجليزي المعروف بملفات `.eml` تجريبية، بحيث تُضاف صيغ جديدة (عربية/تركية) بإضافة محلّل وملف اختبار فقط. حين يرفق صاحب المشروع رسائله تُضاف إلى `tests/fixtures/emails/` بعد تنقيح الأسماء.

### 5.4 إعادة التحليل
زر "إعادة تحليل" على الرسائل `failed` و`ignored` (مفرد/جماعي) يشغّل المحلّلات الحالية على `raw_emails` المحفوظة دون اتصال بالبريد — مفيد بعد تحديث البرنامج بمحلّل جديد.

## 6. الشاشات

**الهيكل العام**: شريط جانبي على اليمين (شعار، روابط الشاشات مع عدّادات، زر قفل، تبديل المظهر)، ومحتوى على اليسار. نافذة بحد أدنى 1100×700. إشعارات toast أسفل اليسار. كل عملية مالية تطلب تأكيداً.

**محاذاة الجداول (كل الجداول: المعاملات، معاملات العميل، الدفتر، العملاء، الرسائل، سجل السحب)** — طلب صاحب المشروع بعد 0.2.2 حيث ظهرت الأعمدة غير متطابقة والمبالغ مقصوصة عند الحافة:
- **العنوان فوق محتواه تماماً**: لكل عمود عرض ثابت (أو `minmax`) ومحاذاة واحدة يشترك فيها العنوان والخلايا. الجدول `table-layout: fixed` (أو شبكة CSS موحّدة للرأس والصفوف).
- **النصوص** (المرسل، الملاحظة، العميل، الوصف): محاذاة بداية السطر (يمين في RTL)، سطر واحد مع `…` وتلميح بالنص الكامل عند المرور.
- **المبالغ**: كل أعمدة المبالغ بنفس المحاذاة (نهاية العمود، أي اليسار في RTL)، أرقام بعرض ثابت (`font-variant-numeric: tabular-nums`)، والرقم داخل `<bdi dir="ltr">`، ورمز العملة في حيّز بعرض ثابت بعد الرقم، فتتطابق الفواصل العشرية عمودياً. المبلغ لا يُقصّ أبداً.
- **التاريخ**: سطران (التاريخ ثم الوقت) بنفس المحاذاة في كل الصفوف.
- **خلية المرسل**: الاسم في السطر الأول (إن غاب: الإيميل؛ وإن غابا: "—")، وسطر ثانٍ أصغر برقم المعاملة. الشارات ("تحتاج مراجعة"، "تحتاج رسوم") في موضع ثابت لا يزيح النص ولا يغيّر عرض العمود.
- **لا قصّ عند الحافة**: الأعمدة تتسع للنافذة؛ إن ضاقت النافذة عن مجموع العروض يظهر تمرير أفقي **داخل إطار الجدول** (مع تثبيت عمود التحديد/التاريخ وعمود ⋯)، لا قصّ للصفحة.
- ارتفاع صف ثابت، وصف الإجماليات بنفس أعمدة الجدول تماماً.

- **شريط إجراءات جماعية**: تخصيص لعميل · استبعاد/إرجاع · حذف.
- **إجراءات الصف**: تخصيص · تعديل الرسوم · تعديل البيانات/تأكيد المراجعة · استبعاد/إرجاع · حذف · عرض التفاصيل.
- **لوحة التفاصيل (جانبية)**: كل الحقول، تفصيل الحساب، ملاحظة المدير، سجل التغييرات من `audit_log`، و"عرض الرسالة الأصلية" (iframe معزول بلا سكربتات ولا صور خارجية). نفس اللوحة تُستخدم في صفحة العميل.
- **نافذة الرسوم**: حقلان مترابطان (الرسوم/الصافي) · "بلا رسوم" · اقتراح تقديري إن فُعّل.
- **إضافة يدوية**: التاريخ · المرسل · الإيميل · العملة · الأصلي · الرسوم · رقم معاملة PayPal (اختياري) · ملاحظة. تدخل الوارد غير مخصّصة.

**البحث الشامل** (مربع بحث أعلى الشاشة، وأيضاً اختصار `Ctrl+K` من أي شاشة): يبحث برقم المعاملة، اسم/إيميل المرسل، ملاحظة المرسل، أو المبلغ في **كل** المعاملات بكل حالاتها. النتائج قائمة منسدلة (حتى 50): التاريخ · المرسل · المبلغ · **مكانها** (الوارد / مستبعدة / اسم العميل + بانتظار الموافقة أو معتمدة). الضغط على نتيجة يفتح مكانها: الوارد مع تمييز الصف، أو **صفحة العميل على تبويب معاملاته مع تمييز الصف**.

### 6.4 العملاء
- **القائمة**: بحث · فلتر نشط/معطّل · فلتر **"لديهم بانتظار الموافقة"** · أعمدة: الاسم · الهاتف · العمولة الافتراضية · الرصيد (شارة لكل عملة، الأحمر = عليه) · بانتظار الموافقة (عدد، شارة بارزة) · ⋯
- **نافذة إضافة/تعديل**: الاسم (فريد، إلزامي) · الهاتف · العمولة الافتراضية % · ملاحظات · نشط.
- الضغط على عميل يفتح دفتره.

### 6.5 دفتر العميل
- **رأس الصفحة**: الاسم والهاتف · بطاقة رصيد لكل عملة (مجموع ما له · مجموع ما دُفع · **المتبقي**).
- **تبويب لكل عملة**؛ داخله جدول القيود (الأقدم أولاً): التاريخ · النوع · الوصف · له (+) · عليه (−) · **الرصيد الجاري** · المرجع · ⋯ (عكس القيد / فتح المعاملة).
  - وصف قيد الاعتماد تلقائي: "دفعة من {المرسل} — أصلي {gross}، رسوم {fee}، عمولة {x%}".
  - القيود المعكوسة تظهر مشطوبة مع رابط للقيد العكسي.
- **فلتر فترة** مع سطر "رصيد سابق" في أعلى الجدول عند تحديد بداية.
- **أزرار**: تسجيل دفعة · قيد تسوية · تصدير CSV · تصدير Excel (6.8) · طباعة/PDF (كشف حساب عربي نظيف: الاسم، الفترة، الجدول، الرصيد الختامي).
- **تبويب "معاملاته"** (هنا تنتقل المعاملات بعد التخصيص): تبويبان فرعيان بعدّادات **بانتظار الموافقة** (يُفتح افتراضياً إن كان فيه شيء) · **معتمدة**.
  - أعمدة: ☐ · التاريخ · المرسل · ملاحظة المرسل · الأصلي · الرسوم · الصافي · العمولة % · العمولة · للعميل · ⋯، وصف إجماليات لكل عملة. نفس قواعد المحاذاة.
  - إجراءات بانتظار الموافقة (مفرد وجماعي): **اعتماد** · تعديل الرسوم · تعديل العمولة · تعديل البيانات/تأكيد المراجعة · **إلغاء التخصيص** (تعود للوارد) · نقل لعميل آخر (= إلغاء التخصيص ثم تخصيص) · حذف.
  - إجراءات المعتمدة: إلغاء الاعتماد (بسبب؛ تعود للوارد مع قيد عكسي) · حذف · عرض التفاصيل.
  - تبويب **معتمدة** وجدول الدفتر: شريط التحديد فيه **«إضافة إلى ملف العميل»** (6.8.2)، وعمود صغير ✓ "في ملف العميل".
  - الاعتماد الجماعي يعرض المجموع لكل عملة في التأكيد.

### 6.6 الرسائل
- تبويبات: فاشلة · متجاهلة · محلَّلة.
- أعمدة: التاريخ · من · الموضوع · السبب · البريد.
- إجراءات: عرض الرسالة · إعادة تحليل (مفرد/جماعي) · "إنشاء معاملة يدوياً من هذه الرسالة" (تُربط بـ `raw_email_id`) · "تجاهل".

### 6.7 الإعدادات
- **البريد**: قائمة الحسابات (التسمية، العنوان، آخر سحب) · إضافة/تعديل · اختبار الاتصال · تغيير كلمة المرور · إيقاف · حذف (فقط إن لم تكن له معاملات).
- **سجل السحب**: جدول `pull_runs` مع عمود النطاق.
- **نطاقات PayPal الإضافية** (5.6): حقل قائمة، مع عرض القائمة المدمجة للقراءة.
- **العمولة والرسوم**: العمولة الافتراضية للعملاء الجدد · تقدير الرسوم (تفعيل، نسبة، ثابت).
- **النسخ الاحتياطي**: المجلد · نسخ عند الإغلاق · عدد النسخ المحفوظة (30) · "نسخة الآن" · "استعادة من ملف" (تأخذ نسخة من الحالية أولاً ثم تعيد تشغيل البرنامج) · قائمة آخر النسخ.
- **الأمان**: تفعيل/تغيير كلمة القفل · قفل تلقائي بعد N دقيقة خمول.
- **Excel**: مسار الملف الرئيسي ("اختيار ملف") · "تحديث ملف Excel" · "فتح الملف" · وقت آخر تحديث · تحديث تلقائي عند إغلاق البرنامج.
- **المظهر**: داكن/فاتح/حسب النظام.
- **حول**: الإصدار · مسار ملف البيانات · "فتح مجلد البيانات" · "التحقق من التحديثات" · خيار "التحقق تلقائياً عند التشغيل" (مفعّل افتراضياً) (6.9).

### 6.8 التصدير إلى Excel

اتجاه واحد فقط: البرنامج ← Excel (لا استيراد).

**الملف الرئيسي (يُحدَّث دائماً)**
- يختار المدير مساراً مرة واحدة (نافذة حفظ بفلتر `.xlsx`) فيُحفظ في الإعدادات.
- زر **"تحديث ملف Excel"** يحدّث نفس الملف، مع وقت آخر تحديث وزر "فتح الملف". **الوضع الافتراضي "إضافة الجديد"** (6.8.1): يحفظ كل ما كتبه المدير داخل الملف. الوضع البديل "إعادة كتابة كاملة" (السلوك القديم) خيار في الإعدادات.
- خيار: تحديث الملف تلقائياً عند إغلاق البرنامج (مع النسخة الاحتياطية؛ فشله لا يمنع الإغلاق ويُسجَّل).
- الكتابة إلى ملف مؤقت في نفس المجلد ثم استبدال، فلا يتلف الملف القديم عند الفشل. إن كان مفتوحاً في Excel (ويندوز يقفله) ⇒ خطأ `file_locked`: "أغلق الملف في Excel ثم أعد المحاولة".

#### 6.8.1 وضع "إضافة الجديد" (الافتراضي) — طلب صاحب المشروع

المدير يكتب داخل ملف Excel (ملاحظات، ألوان، أعمدة إضافية، معادلات، أوراق خاصة به). التحديث **لا يمسح شيئاً من ذلك**:

- **ورقة "المعاملات"**:
  - **المعاملات الجديدة** (التي لم تُصدَّر لهذا الملف من قبل) **تُضاف صفوفاً في آخر الجدول** بنفس تنسيق الصفوف الموجودة، ويتمدد نطاق الجدول/الفلتر ليشملها.
  - **الصفوف الموجودة**: يُحدَّث فيها **فقط** أعمدة البرنامج التي تغيّرت قيمتها (العميل، العمولة، للعميل، الحالة، الرسوم، الصافي، اسم المرسل…) بمطابقة **رقم PayPal**. الأعمدة الإضافية التي أنشأها المدير، والتنسيق، والألوان، والتعليقات، والمعادلات **لا تُلمس**.
  - معاملة **حُذفت** من البرنامج: صفّها **لا يُحذف**؛ عمود الحالة يصبح "محذوفة".
  - صف حذفه المدير بنفسه من الملف: **لا يُعاد** (التتبع في قاعدة البيانات، أدناه).
  - أعمدة البرنامج تُعرف **باسم العنوان** لا بموقعه، فيمكن للمدير نقلها أو إضافة أعمدة بينها. إن حُذف أو أُعيدت تسمية عنوان عمود من أعمدة البرنامج ⇒ لا يُكتب شيء، وخطأ `excel_layout`: "لم أجد عمود «{الاسم}» في ورقة المعاملات. أعد العنوان كما كان أو اختر «إعادة كتابة كاملة»."
- **أوراق "الملخص" و"العملاء" و"الدفتر"**: تُعاد كتابتها كاملة في كل تحديث (لقطة من البرنامج)، وتحمل في أعلاها سطراً: "هذه الورقة يكتبها البرنامج عند كل تحديث — لا تكتب فيها". **أي ورقة أخرى أضافها المدير لا تُلمس.**
- **أول مرة / الملف غير موجود**: يُنشأ الملف كاملاً كما في الوضع القديم.
- **قبل كل تحديث** تُحفظ نسخة من الملف السابق باسم `{الاسم}.previous.xlsx` بجانبه (واحدة فقط، تُستبدل كل مرة)؛ والكتابة عبر ملف مؤقت ثم استبدال كما سبق.
- **النتيجة** تعرض: "أُضيفت N معاملة جديدة، حُدّث M صفاً".
- **التتبع**: جدول جديد
  ```sql
  CREATE TABLE excel_exported (
    file_path      TEXT NOT NULL,
    paypal_txn_id  TEXT NOT NULL,
    exported_at    TEXT NOT NULL,
    PRIMARY KEY (file_path, paypal_txn_id)
  );
  ```
  الإضافة = معاملات ليست في هذا الجدول **ولا** موجودة أصلاً في عمود رقم PayPal في الورقة (حماية من التكرار إن أُعيد بناء القاعدة). تغيير مسار الملف يبدأ تتبعاً جديداً لذلك المسار.
- **المكتبة**: تعديل ملف موجود مع الحفاظ على تنسيقه يحتاج مكتبة قراءة/كتابة (مثل `umya-spreadsheet`)؛ تتحقق جلسة القلب من أنها تحفظ التنسيق والأعمدة الإضافية والأوراق الأخرى والمعادلات (اختبار ذهاب وإياب على ملف فيه كل ذلك) قبل اعتمادها. `rust_xlsxwriter` يبقى للإنشاء الأول وللتصديرات السريعة.
- **التصديرات السريعة** (المعاملات، كشف العميل) تبقى ملفاً جديداً كل مرة.

#### 6.8.2 ملف Excel للعميل (كشف حساب يُسلَّم للعميل) — طلب صاحب المشروع

يحلّ محل فكرة "الإضافة لأي ملف" (أُلغيت قبل التنفيذ). المدير **يعطي العميل ملف Excel لا البرنامج**. لكل عميل ملف واحد مرتبط به، يضيف إليه المدير **بيده** ما يريد، ويبقى قابلاً للتعديل منه (تعديلاته محفوظة كما في 6.8.1).

**الربط** (رأس صفحة العميل، بطاقة "ملف Excel للعميل"):
- غير مرتبط: **"إنشاء ملف للعميل"** (نافذة حفظ، الاسم الافتراضي `كشف حساب - {الاسم}.xlsx`) مع خيار "أضف كل الحوالات المعتمدة والدفعات الحالية" (معطّل افتراضياً، يعرض العدد)؛ أو **"ربط ملف موجود"** (يجب أن يكون ملف كشف أنشأه البرنامج لهذا العميل؛ يُعرف بخاصية مستند مخفية `PpFeezCustomerId`، وإلا `excel_layout`).
- مرتبط: المسار · آخر تحديث · **فتح الملف** · فتح المجلد · تغيير الملف · إلغاء الربط (لا يحذف الملف).

**شكل الملف** (عربي RTL، أنيق، جاهز للتسليم):
- **ورقة لكل عملة** باسم `كشف USD`، `كشف EUR`… تُنشأ عند أول سطر بتلك العملة.
- **رأس الورقة** (أعلى الجدول): "كشف حساب — {اسم العميل}" · العملة · **إجمالي المستحق له** · **إجمالي المدفوع له** · **الرصيد الحالي** (معادلات `SUM` على أعمدة الجدول فتبقى صحيحة مهما أُضيف أو عُدّل) · تاريخ آخر تحديث.
- **جدول Excel** (اسمه `Statement_USD`…) بالأعمدة بالترتيب:

| # | العمود | سطر حوالة | سطر دفعة/تسوية |
|---|---|---|---|
| 1 | التاريخ | تاريخ الحوالة | تاريخ القيد |
| 2 | البيان | "حوالة PayPal من {المرسل}" (+ ملاحظة المرسل إن وجدت) | "دفعة — {الطريقة}" / وصف التسوية / "عكس: …" |
| 3 | رقم الحوالة / المرجع | رقم PayPal | مرجع الدفعة |
| 4 | الحوالة من PayPal | الأصلي | — |
| 5 | خصم PayPal | الرسوم | — |
| 6 | الصافي من PayPal | الصافي | — |
| 7 | العمولة المطبقة % | النسبة (أو "مبلغ ثابت") | — |
| 8 | قيمة العمولة | العمولة | — |
| 9 | الصافي لك | المبلغ للعميل | تسوية موجبة |
| 10 | دُفع لك | — | الدفعة / تسوية سالبة / العكس |
| 11 | الرصيد | **معادلة**: الرصيد السابق + الصافي لك − دُفع لك | نفس المعادلة |

  وعمود مخفي أخير `مفتاح` (`T:{رقم PayPal}` أو `L:{رقم القيد}`) لكشف التكرار. تنسيق المبالغ حسب خانات العملة، أرقام بعرض ثابت، صف عناوين مثبّت، ألوان هادئة، عرض أعمدة مناسب.

**ما يُضاف** (بيد المدير فقط):
- **حوالات معتمدة فقط** (غير المعتمدة تُرفض مع السبب).
- **قيود الدفتر غير الاعتمادية**: الدفعات، التسويات، قيود العكس (إلغاء اعتماد حوالة مضافة يظهر هكذا كسطر "عكس" إن أضافه المدير).
- الأماكن: صفحة العميل ← معاملاته ← **معتمدة** (تحديد ثم «إضافة إلى ملف العميل»)؛ الدفتر (تحديد قيود ثم نفس الزر)؛ نافذة **الاعتماد** ونافذة **تسجيل دفعة** فيهما خيار "أضف إلى ملف العميل" (يُتذكَّر آخر اختيار لكل عميل).
- داخل الدفعة الواحدة تُرتَّب الأسطر بالتاريخ ثم تُضاف في **آخر** الجدول. سطر تاريخه أقدم من آخر سطر في الكشف يُضاف مع تنبيه معلوماتي.

**التكرار** (طلب صريح):
- قبل الكتابة معاينة: "ستُضاف N"، و**"موجودة أصلاً في ملف العميل: M"** مع قائمتها (التاريخ، المبلغ، رقم الحوالة). الموجودة **لا تُضاف**.
- المطابقة بجدول التتبع **و**بعمود `مفتاح` في الملف معاً (فإن حذف المدير سطراً من الملف يمكن إضافته من جديد، وإن أعاد بناء القاعدة لا يتكرر شيء).
- في الجداول: ✓ "في ملف العميل" بجانب كل حوالة/قيد مضاف. حوالة أُضيفت ثم **أُلغي اعتمادها أو حُذفت**: شارة "تغيّرت بعد إضافتها لملف العميل" (يقرر المدير إضافة سطر العكس).

**الكتابة**: نفس المحرك الجراحي (6.8.1): ما عدا الورقة المستهدفة ومتطلباتها يُنسخ كما هو؛ صفوف جديدة بتنسيق الصف السابق؛ تمدد الجدول؛ `.previous.xlsx`؛ ملف مؤقت ثم استبدال؛ تحقق ذاتي؛ `file_locked`؛ `excel_layout` إن تغيّرت بنية الجدول.

**التتبع**:
```sql
CREATE TABLE customer_excel (
  customer_id  INTEGER PRIMARY KEY REFERENCES customers(id),
  file_path    TEXT NOT NULL,
  updated_at   TEXT
);
CREATE TABLE customer_excel_items (
  customer_id  INTEGER NOT NULL,
  file_path    TEXT NOT NULL,
  item_kind    TEXT NOT NULL CHECK (item_kind IN ('txn','ledger')),
  item_id      INTEGER NOT NULL,
  currency     TEXT NOT NULL,
  added_at     TEXT NOT NULL,
  PRIMARY KEY (customer_id, file_path, item_kind, item_id)
);
```
حذف العميل (4.7) يحذف صفوفه هنا ولا يمسّ الملف.

أوراق الملف (كلها RTL، رأس مثبّت، فلتر تلقائي، عرض أعمدة مناسب، عناوين عربية):

| الورقة | المحتوى |
|---|---|
| الملخص | لكل عملة: الوارد، الرسوم، عمولتي، المستحق للعملاء، المدفوع (كل الفترات)؛ عدد غير المخصّص/تحتاج رسوم/بانتظار الموافقة؛ وقت التصدير |
| المعاملات | التاريخ، رقم PayPal، النوع، المرسل، الإيميل، ملاحظة المرسل، العملة، الأصلي، الرسوم، الصافي، العميل، العمولة %، العمولة، للعميل، الحالة، البريد، ملاحظة المدير |
| العملاء | الاسم، الهاتف، العمولة الافتراضية، الحالة، ثم عمود رصيد لكل عملة موجودة |
| الدفتر | العميل، العملة، التاريخ، النوع، الوصف، له، عليه، الرصيد الجاري (لكل عميل وعملة)، المرجع، الطريقة، معكوس؟ |

**تصديرات سريعة (ملف جديد كل مرة، مسار من نافذة حفظ)**
- المعاملات: ما هو معروض بالفلتر والترتيب الحاليين (كل الصفحات) + صف إجماليات لكل عملة.
- دفتر العميل: كشف حساب، ورقة لكل عملة (أو العملة المحددة): رأس باسم العميل والفترة، رصيد سابق، القيود، الرصيد الختامي.

**قواعد**
- المبالغ تُكتب **أرقاماً** لا نصاً (ليعمل الجمع في Excel)، بتنسيق حسب خانات العملة (`#,##0.00` أو `#,##0`). التحويل من الأعداد الصحيحة إلى رقم Excel يحدث **فقط** لحظة الكتابة للملف.
- التواريخ تواريخ Excel حقيقية بتوقيت الجهاز.
- المكتبة: `rust_xlsxwriter` (تحقق من إصدارها الحالي)؛ والاختبارات تقرأ الملف بـ `calamine`.

### 6.9 التحديث التلقائي

**التجربة عند صاحب البرنامج**
- عند التشغيل (بعد فتح القفل) وبشكل صامت، إن كان الخيار مفعّلاً، يتحقق البرنامج من وجود نسخة أحدث. لا رسالة إن لم توجد أو تعذّر الاتصال.
- إن وُجدت: شريط/نافذة "يتوفر إصدار جديد {version}" مع ملاحظات الإصدار بالعربية، وزرّان: **تحديث الآن** · **لاحقاً** (يُذكّر في التشغيل التالي).
- "تحديث الآن":
  1. إن كانت هناك عملية سحب جارية ⇒ يُطلب انتظارها أو إلغاؤها أولاً.
  2. **نسخة احتياطية تلقائية** (`backup_now`). إن لم يُحدَّد مجلد نسخ: تحذير يطلب تحديده أو المتابعة صراحة.
  3. تنزيل مع شريط تقدّم ← تثبيت (وضع NSIS `passive`) ← إعادة تشغيل البرنامج تلقائياً.
- الإعدادات ← حول: الإصدار الحالي، زر "التحقق من التحديثات" (يُظهر "لديك أحدث إصدار" إن لم يوجد)، وخيار التحقق التلقائي.
- البيانات لا تتأثر بالتحديث (في `%APPDATA%`)، والـ migrations الجديدة تُطبَّق تلقائياً عند أول تشغيل.
- الأخطاء بالعربية: لا اتصال، فشل التنزيل، فشل التحقق من التوقيع (يُرفض التحديث ولا يُثبَّت).

**التقنية**
- `tauri-plugin-updater` + `tauri-plugin-process` (لإعادة التشغيل). `bundle.createUpdaterArtifacts = true`. الـ endpoint:
  `https://github.com/MohammedM98/PpFeez/releases/latest/download/latest.json`.
- التحديثات **موقّعة**: المفتاح العام في `tauri.conf.json` (`plugins.updater.pubkey`)، والمفتاح الخاص وكلمة مروره في GitHub Secrets فقط: `TAURI_SIGNING_PRIVATE_KEY` و `TAURI_SIGNING_PRIVATE_KEY_PASSWORD`. **لا يُرفع المفتاح الخاص إلى المستودع ولا يُكتب في أي محادثة أبداً.** صاحب المشروع ينشئ المفتاحين على جهازه ويضيف السرّين بنفسه، ويعطي الجلسة المفتاح العام فقط.
- المستودع يجب أن يبقى **عاماً** ليعمل التحديث (الـ Releases تُقرأ بلا تسجيل دخول). إن صار خاصاً يتوقف التحديث التلقائي.

**الإصدارات والنشر**
- `version` في `src-tauri/tauri.conf.json` هو رقم الإصدار (و `package.json` بنفس الرقم). يُعرض في "حول" وفي اسم ملف التثبيت.
- **قاعدة الرفع**: عند إنهاء ميزة أو إصلاح جاهز للمستخدم ترفع الجلسة الرقم (`0.2.0` لميزة، `0.2.1` لإصلاح) وتضيف قسماً بالعربية في أعلى `docs/CHANGELOG.md` بنفس الرقم. الالتزامات العادية أثناء العمل لا ترفع الرقم.
- workflow البناء: بعد نجاح الاختبارات والبناء، إن لم يوجد Release بوسم `v{version}` **وكان** السرّ `TAURI_SIGNING_PRIVATE_KEY` موجوداً ⇒ ينشر GitHub Release (غير مسودة) بالوسم `v{version}`، فيه ملف التثبيت و `latest.json`، ونصه قسم الإصدار من `CHANGELOG.md`. إن لم يوجد السرّ ⇒ يبني artifact كما الآن بلا Release ولا يفشل.
- الإصدار الحالي المثبّت `0.1.0` لا يحتوي المحدّث: أول إصدار به (`0.2.0`) يُثبَّت يدوياً مرة أخيرة، وما بعده تلقائي.

## 10. التحقق (Verification)

**`cargo test` (في `crates/core`)**
- `money`: تحليل وتنسيق المبالغ بالصيغ الأربع، عملات بلا كسور.
- `commission`: مثال 100/5/25% = 23.75/71.25، التقريب half-up عند .5، نسبة 0 و100%، مبلغ ثابت، رفض عمولة أكبر من الصافي.
- دورة الحياة: كل انتقال مسموح، ورفض كل انتقال ممنوع (اعتماد بلا رسوم، تعديل معتمدة، تخصيص لعميل معطّل...).
- الدفتر: قيد واحد عند الاعتماد، فشل UPDATE/DELETE، عدم عكس القيد مرتين، الرصيد لكل عملة، الرصيد الجاري، إلغاء الاعتماد يعيد الرصيد لما كان.
- الاسترداد: كامل وجزئي، قبل وبعد الاعتماد.
- المصدر: قبول PayPal مع `dkim=pass`، رفض اسم ظاهر مزوّر، رفض `dkim=fail`، تجاهل ترويسة Authentication-Results مزروعة أسفل ترويسة Google.
- المحلّلات: كل ملف `.eml` يعطي الحقول المتوقعة؛ رسالة غير مالية ⇒ `ignored`؛ ناقصة ⇒ `failed`.
- السحب بجالب وهمي: دفعات، تحديث `last_uid`، سحب ثانٍ بلا تكرار، تغيّر `UIDVALIDITY`، خطأ في المنتصف ثم استكمال.
- المحلّلات (5.3): لكل نوع في الجدول ولكل لغة (en/he/ar/tr) ملف `.eml` تجريبي واحد على الأقل يعطي الحقول الصحيحة؛ المحلّل العام يلتقط رسالة بصيغة غير معروفة ويضع `needs_review`؛ معاملة `needs_review` لا تُعتمد قبل التأكيد؛ eCheck معلّق ثم مكتمل يحدّث نفس المعاملة؛ رسالة on hold لا تنشئ معاملة جديدة.
- نطاق غير معروف (5.6): `paypal.xx` مع DKIM صحيح ⇒ `ignored: unknown_paypal_domain`؛ "الوثوق بهذا النطاق" يضيفه ويعيد تحليل رسائله فتنشأ المعاملات.
- ملف العميل (6.8.2): إنشاء بورقة لكل عملة ورأس بمعادلات SUM صحيحة؛ أعمدة الجدول بالترتيب ومعادلة الرصيد الجاري (حوالة 100/5/95/25%/23.75/71.25 ثم دفعة 50 ⇒ رصيد 21.25)؛ رفض حوالة غير معتمدة؛ المكرر يُكتشف بالتتبع وبعمود المفتاح ولا يُضاف؛ سطر حذفه المدير يمكن إضافته؛ تعديلات المدير في الملف وأوراقه الأخرى تبقى بايتاً؛ ربط ملف لعميل آخر ⇒ `excel_layout`؛ `file_locked`؛ حذف العميل يحذف التتبع لا الملف.
- Excel إضافة الجديد (6.8.1): على ملف فيه عمود إضافي للمدير وألوان وتعليق ومعادلة وورقة خاصة: التحديث يضيف الجديد فقط ويحدّث أعمدة البرنامج المتغيرة ويبقي كل ما سبق (قراءة بـ `calamine` وفحص التنسيق)؛ صف حذفه المدير لا يعود؛ معاملة محذوفة تصير "محذوفة"؛ عنوان عمود ناقص ⇒ `excel_layout` ولا كتابة؛ `.previous.xlsx` يُنشأ؛ ملف مقفول ⇒ `file_locked` والملف سليم؛ تحديثان متتاليان بلا تغيير ⇒ 0 مضافة 0 محدّثة.
- الوارد (6.3): التخصيص يُخرج المعاملة من `txn_list` الافتراضي ويُظهرها في قائمة العميل؛ إلغاء التخصيص يعيدها؛ `txn_search_all` يجد المعاملة بكل حالاتها ويعيد مكانها؛ `customers_list({hasPending:true})` صحيح.
- المحاذاة (الهيكل العام 6): Playwright عند 1100×700 و1920×1080 بالوضعين، ببيانات فيها أسماء طويلة ومبالغ مثل 1,234,567.89 وعملات مختلفة: لكل عمود، حدود العنوان الأفقية تطابق حدود خلاياه (±1px)؛ لا خلية مبلغ مقصوصة (`scrollWidth <= clientWidth`)؛ الفواصل العشرية متطابقة في عمود المبالغ؛ لا تمرير أفقي للصفحة.

- نطاقات PayPal (5.6): رسالة من `service@paypal.co.il` بتوقيع `dkim=pass header.d=paypal.co.il` تُقبل؛ نطاق إضافي من الإعدادات يُقبل؛ `paypal.co.il.evil.com` و`paypal-co-il.com` و`From` بنطاق معتمد مع DKIM لنطاق آخر تُرفض؛ ترويسة `ARC-Authentication-Results` لا تُعامل كـ `Authentication-Results`؛ الاستعلام `{PAYPAL_FROM}` يُبنى صحيحاً لنطاق واحد ولعدة نطاقات.
- الواجهة: فلتر العملة في المعاملات افتراضياً **كل العملات**؛ سطر "آخر سحب" يعرض: مقروءة/جديدة/مكررة/متجاهلة/فاشلة، ويعرض عند 0 نتائج: "لم تُوجد رسائل من PayPal في هذه الفترة" مع النطاقات التي بُحث عنها.
- نطاق السحب: `last_days` و `between` يجلبان فقط الرسائل داخل الفترة (بما فيها رسالة في آخر دقيقة من يوم `to` ورسالة قبل منتصف ليل `from` بتوقيت مختلف)؛ سحب نفس الفترة مرتين بلا تكرار؛ `last_uid` لا ينقص بعد سحب فترة قديمة؛ `new` بعد سحب فترة يجلب ما بعدها؛ رفض `from > to` والتواريخ المستقبلية بـ `invalid_range`.
- النسخ والاستعادة.
- Excel: الأوراق الأربع بعناوين عربية و RTL؛ المبالغ أرقام بقيم صحيحة (100.00/5.00/95.00/23.75/71.25) وعملة بلا كسور؛ `excel_update` مرتين يعيد كتابة نفس المسار بالبيانات الجديدة؛ ملف مقفول ⇒ `file_locked` والقديم سليم؛ بلا مسار ⇒ `no_export_path`؛ تصدير المعاملات يحترم الفلتر؛ كشف الدفتر يطابق الرصيد الجاري.
